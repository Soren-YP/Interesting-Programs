# Distinctive Frontend

这个 skill 不给你风格，只给你一套逼自己离开默认值的过程。提炼自 Anshu Chimala
《How to turn your AI into a world-class designer》（Lenny's Newsletter, 2026-09），
并结合 motionsites.ai 案例的观察，改写为适用于"每天使用的工具型应用"。

## 先理解问题：为什么 AI 设计会平庸

模型逐 token 生成设计，每遇到一个设计决策（颜色、布局、字体、间距）都会选"最可能让所有人
满意"的那个。结果就是设计委员会的终极形态：紫色渐变、左文右图、圆角卡片、同一种阴影。

- **"请做得独特一点 / 随机一点"没有用**：模型只会预测"听起来随机"的 token，结果依然雷同。
- **多样性必须从模型外部注入**：随机种子、用户的品味、参考图、独立的评审者。
- **AI 爱加不爱减**：删代码、删元素对模型来说是"风险"，需要被明确推动。

因此本 skill 的每一步都在做同一件事：**在关键决策点上，不接受第一反应。**

## 硬性原则

1. **不预设风格。** 本文件和 references 里没有任何调色板、字体或布局推荐，也不要从记忆里
   套用"好看的默认值"。风格只能来自下面的发散过程和用户的反应。
2. **功能先于形式，但形式不迁就旧结构。** 所有功能必须保留并通过测试（见
   [references/star-context.md](references/star-context.md)）；而 DOM 结构、信息层级、
   组件形态都可以推翻重来。
3. **用户是品味的来源。** 方向要让用户选、让用户反应，再根据反应收紧。不要替用户拍板。
4. **用眼睛验收，不用代码验收。** 每一轮都要在真实浏览器里截图看效果；jsdom 测试只证明功能。

## 流程

### 阶段一 · Discover：先走宽，再走深

**1. 种子字符串注入随机性（String Seed of Thought）**

用 shell 生成一个真正随机的字符串，让它成为灵感来源，而不是模型的训练默认值：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

对每个种子：从字符串里寻找子模式、特殊数字、字母组合、节奏，把它们"翻译"成一个创作方向
（色彩、版式、字体气质、材质、动效性格）。**不要在设计里显示字符串**，它只用于启发。
需要几个方向就生成几个种子，每个方向独立推导，彼此不参考。

**2. 宽泛的概念清单，再由用户收窄**

另列一份 10–20 条的设计语言概念清单：每条一句话，故意不写细节，目的是激发想象而非给方案。
概念可以来自任何领域：一件实物、一个场所、一种工艺、一部电影的美术、一种印刷品、一个时代。
"听起来不可能做成"的点子保留——这往往正是对的方向。

**3. 把方向呈现给用户，记录反应**

把种子方向和概念清单里最有张力的 3–5 个整理给用户（每个附一句话描述 + 它会如何体现在
这个产品的具体界面上）。必要时为前 2–3 个做静态视觉样张（单屏 HTML，不接逻辑）并截图。
用 AskUserQuestion 或直接对话请用户反应，重点捕捉**否定**：
"这个太卡通""灰色渐变很无聊""要有触感但不要拟物"——否定比肯定更能定义品味。

**4. 写一份大胆的设计 brief**

根据用户的反应收紧成一份 brief（存到 `design/brief.md`），包含：
- 一句话概念（这个界面"是"什么，而不是"像"什么网站）
- 情绪目标：用户打开它时应该感受到什么
- 明确拒绝的东西（来自用户的否定）
- 这个概念落在本产品哪些具体时刻（见下方"工具型应用的落点"）
- 一个"标志性细节"：只属于这个设计、别人一眼认得出的那一处

brief 是之后所有决策和评审的依据。

### 阶段二 · Define：用独立评审者推出个性

初稿永远会回到老套路（顶部导航、左侧栏、卡片网格）。这一阶段靠**外部评审循环**推动它。

**5. 设计评审子代理循环**

实现者（你）无法客观评价自己：你看得到代码、记得每个决定的理由。所以由一个**全新上下文的
评审子代理**来判断，它只看截图。

每一轮：
1. 在真实浏览器中截图（桌面宽度为主；必要时加移动端、深色模式、关键交互状态的截图）。
   截图方法见 [references/star-context.md](references/star-context.md)。
2. 用 Agent 工具启动评审者：`model: "fable"`（评审用大模型，实现用当前模型；
   Fable 需要额外额度，返回 429 时改用 `model: "opus"`），
   prompt 使用 [references/critic-prompt.md](references/critic-prompt.md) 的**固定原文**，
   只附截图路径、brief 中的"一句话概念"和参考图路径（若有）。
   **不要**附代码、实现说明、之前的评审或你的辩解。
3. 根据评审给出的最大差距修改，然后进入下一轮。

停止条件（只写在这里，**不写进评审 prompt**，保持其评分客观）：
- 评审独立给出 ≥ 9/10 即完成。
- 先跑 1–2 轮观察是否收敛；若连续两轮分数不升或评审意见开始自相矛盾，停下来把截图和
  评审意见交给用户判断，不要无止境地取悦评审者。

提高评审质量的方法（越往下越好）：
- 差："看看这个设计美不美，像不像 AI 做的"——太主观，每次结果飘忽。
- 可以："先判断设计想表达的美学，想象顶级设计工作室会怎么执行，再比较差距"。
- 好：给评审 4 张专业参考 + 1 张我们的截图，让它**按精致度和品味排名**。参考图放在
  `design/references/`（由用户收集，或用户认可的截图/概念图）。告诉评审参考图是基准和情绪板，
  不是要抄的目标。

**6. 用图像丰富设计（可选，需用户提供工具）**

代码型代理倾向用渐变、几何形状、纹理 CSS 代替真实图像，这本身就是 AI 痕迹。如果设计方向需要
插图、材质、空状态图等，**先问用户**是否有图像生成途径（Codex CLI 订阅、OpenAI / Gemini /
fal.ai 密钥）。密钥只放在被 gitignore 的 `.env.agents`，绝不写进代码或产物。用户没有就跳过，
改用排版和留白解决，不要用假图像糊弄。

视频生成（循环动画、状态间过渡帧）在落地页里威力很大，但对日常工具通常过重；只有 brief 明确
需要且不影响性能时才考虑。

### 阶段三 · Deliver：打磨，主要靠删

**7. 删掉不提供价值的东西**

大部分打磨工作是**删除**。逐个元素问："它不在了，用户会失去什么？"答不上来就删。
典型删除对象：装饰性光晕和渐变、无意义的色块高亮、重复表达同一信息的标签、
多余的容器和边框、解释显而易见之事的说明文字、比原生控件更差的自定义控件。
克制本身就是高级感。

**8. 清除 AI 痕迹**

对照 [references/ai-tells.md](references/ai-tells.md) 逐条检查最终截图。

**9. 交付验收**

- `npm test` 全部通过，`npm run build` 成功。
- 浏览器控制台无报错。
- 桌面、平板、手机三种宽度，浅色/深色两种主题都截图检查过。
- 键盘操作（快捷键、焦点可见、Tab 顺序）和 `prefers-reduced-motion` 都可用。
- 把最终截图和 brief 一起给用户看，说明保留了什么、删了什么、还没验证的是什么。

## 工具型应用的落点

motionsites.ai 上的优秀案例大多是落地页：一个强烈的"世界"（书房里的阅读器、调度中心的
终端），一张真实的主视觉，一个明确的焦点。工具型应用不能照搬宏大场面——用户每天打开几十次，
要的是快和清楚。概念应该落在这些**高频时刻**，而不是装饰层：

- **打开的第一秒**：首屏只有一个焦点。用户来这里最常做的那件事，应该不需要寻找。
- **搜索 / 输入**：输入时的反馈、匹配高亮、"回车会发生什么"的预告。
- **列表的节奏**：密度、对齐、行与行之间的呼吸感，这是用户看得最久的地方。
- **悬停与选中**：每一行在悬停、聚焦、选中、拖拽时的状态变化。
- **打开一个收藏的瞬间**：一个微小但有性格的确认。
- **空状态、加载、出错**：这里最能体现个性，又不打扰日常使用。
- **深色模式**：不是颜色反转，而是同一个概念在夜里的样子。

动效要有性格，但必须快（交互反馈 < 200ms），并尊重 `prefers-reduced-motion`。
